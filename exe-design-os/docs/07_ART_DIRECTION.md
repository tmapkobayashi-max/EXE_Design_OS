# 1. 大原則：スライドは「画像＋文字」で作る

**HTMLでカードや表を並べる方式は使わない。**

参照デッキの構造を解析した結果、スライドは18枚とも 1枚のPNG画像だった。
HTMLは画像をめくるビューアにすぎない。

美しさは「レイアウトの精密さ」ではなく **「イラストの質」** から来ている。

```
1スライド = 背景イラスト（文字なし・AI生成） + テキストレイヤー（別で重ねる）
```

この構造を守ると、次の3つが同時に成立する。

- PowerPointでテキストだけ後から直せる
- 画像に書き出せばWebビューアに載る
- ブランド色・フォントはテキストレイヤー側で厳密に固定できる

# 4. イラストのスタイル指定（★ここが品質を決める★）

参照デッキのイラストは、次の特徴で統一されている。

- **手描きの細い線画**＋淡い水彩の陰影
- 彩度は低い。線は濃く、面は薄い
- 人物は無表情に近い穏やかな表情、シンプルな輪郭、影は最小限
- 光の演出は**1本の光る線**だけ。それ以外は光らせない
- 遠景（山・街・建物）はモノクロに近いグレーで、アクセント色だけが色を持つ

EXEでは以下を標準とする。

| 項目 | 指定 |
|---|---|
| 描法 | 細い手描き線画 ＋ 淡い水彩の陰影 |
| 彩度 | 低め。基調はグレー〜生成り |
| 色を持つ要素 | EXE Pink `#FF6366` の光る線・光点のみ |
| 人物 | スーツまたは作業着。表情は穏やか。記号的に簡略化 |
| 視点 | アイソメトリック（俯瞰）または横からのフラット |
| 光源 | 1方向のみ。強い影は作らない |
| 禁止 | 写真的リアリズム、3DCG風の光沢、グラデーションの多用、影の重ね塗り |

# 5. DALL-E 発注プロンプトの型（★コピペ用★）

Codex（ChatGPT上の画像生成）に投げる。**1チャット1画像**。

```
以下のイラストを1枚作ってください。

【構図】
（例：スーツ姿の女性が左端に立ち、そこから1本の光る道が右上の山頂へ伸びていく。
　道の途中に4つの通過点がある。背景は連なる山並み。）

【スタイル】
・細い手描きの線画に、淡い水彩の陰影を乗せた絵柄
・彩度は低く、全体はグレーと生成り色（#F7F3EC に近い紙の色）
・色を持つのは1本の光る道だけ。色は #FF6366（ピンク）のグロー
・光源は1方向のみ。強い影やグラデーションは付けない
・人物は表情を作り込まず、輪郭をシンプルに

【比率】
16:9

【厳守・NG要素】
・文字、数字、単語、ロゴ、記号を画像内に一切描かない
・グラフ、チャート、データパネル、ダッシュボード風の要素を描かない
・看板、タグ、プレート、モニター画面のような矩形パネルを描かない
・写真的なリアリズム、3DCG風の光沢を出さない
・指定した色以外の彩度の高い色を使わない
```

構図欄だけを案件ごとに書き換える。他は固定。

**重要**：文字は絶対に画像に入れさせない。
日本語はAIが正しく描けず、かつ後から直せなくなる。文字はpptx側で重ねる。

# 6. 構図のパターン集

参照デッキで実際に使われていた構図。案件に応じて選ぶ。

| 型 | 構図 | 使いどころ |
|---|---|---|
| **旅路型** | 人物が左端。光る道が右上へ伸び、途中に通過点 | 目次、ステップ、ロードマップ |
| **俯瞰マップ型** | 建物や部屋をアイソメトリックで俯瞰。光る線が各所を巡る | 全体像、システム構成、業務フロー |
| **対峙型** | 人物が右。左に大量の書類や情報が浮遊し、1点に収束 | 課題の可視化、Before/After |
| **斜めカット型** | 画面を濃色の斜め帯で分割。片側に人物、片側に余白 | 表紙、章扉、結論 |
| **道具型** | 細いラインアイコンを縦に並べ、光る縦線でつなぐ | 手順、機能一覧 |

**型は指定する。絵の中身はAIに考えさせる。** これが「大枠は固定、中身は自由」の実装。

# 7. テキストレイヤーの規則

イラストの上に重ねる文字は、以下を厳守する。

| 用途 | サイズの目安（16:9・1920px幅換算） | 色 |
|---|---|---|
| 見出し（Level 2） | 96〜120px・極太 | `#1E1C1C` |
| 大見出し（表紙） | 120〜150px・極太 | `#1E1C1C` |

- 1スライドの文字ブロックは **3つまで**

# 8. AIに渡す自由と、渡さない自由

| AIが決めてよい | AIが決めてはいけない |
|---|---|
| どの構図の型を使うか | 色（HEX指定以外は使用禁止） |
| イラストの具体的な中身・小物・背景 | フォント |
| 見出しの言い回し・語感 | 文字サイズの階層 |
| 情報を何枚に分けるか | 余白の最小値 |
| アイコンの絵柄 | ノンブルの表記と位置 |
| 1枚に載せる要素の数（上限内で） | 図とテキストの比率の下限 |

迷ったら「**色とフォントと余白はEXEのもの。絵と言葉はAIのもの**」と考える。

# 8-2. 画面を埋める（★最も守られない項目★）

余白は「最低40px」であって「たくさん空ける」ではない。
**上下の余りが目立つスライドは失敗**とみなす。

| 症状 | 直し方 |
|---|---|
| 画面の上1/3が空いている | 見出しを上端に寄せ、図を上に引き上げる |
| 図が下半分に沈んでいる | 図の領域を `1fr` にして縦に伸ばす |
| 中央に小さくまとまっている | 図を大きくする。要素を足すのではなく、既存の要素を大きくする |
| 右半分が空いている | 2カラムにして補足・凡例・数字を置く |

判定方法：**スライドを画像に書き出し、上下左右の余白帯が本文領域より広くないか見る。**
広ければ密度不足。図を拡大するか、カラムを増やす。

具体的な目安（1920×1080の場合）：

- 本文・図の領域は、**縦880px・横1712pxのうち8割以上**を使う
- 図は「置く」のではなく「**枠いっぱいに伸ばす**」。SVGの領域を `1fr` にして高さを与える
- 図の左右に200px以上の空きができたら、図が小さすぎる

**全スライドを、その資料の中で最も密度の高い1枚に合わせる。**
1枚だけ詰まっていて他がスカスカ、という状態にしない。

見出しの改行は `<br>` で**明示的に指定する**。
自動折り返しに任せると「に。」だけが行に落ちるなど、意味の切れ目で折れない。

# 8-3. 図はスライドごとに作り分ける

**同じ絵を複数のスライドで使い回さない。** 汎用の飾り図は禁止。

各スライドの図は、そのスライドの主張を絵にしたものでなければならない。

| 主張 | 図の形 |
|---|---|
| 順番がある | 横一列のフロー（3〜4）／縦のフロー（5以上） |
| ぐるぐる回る | 円環。**始点と終点を必ず閉じる**。要素を輪の外に出さない |
| 二つを比べる | 左右対比。中央に太い矢印 |
| 構造・階層 | 入れ子、または上下の積み重ね |
| 時間の経過 | 横一直線のタイムライン |
| 量の大小 | 数字をLevel 1で。棒や円のグラフは使わない |

図に意味のない装飾を足さない。**線1本ごとに「これは何を表すか」を言えること。**

## 8-3-1. 図の中の文字は、図形からはみ出さない

円・四角の中に文字を置くときは、**図形を文字に合わせて大きくする**。
文字を小さくして押し込むのではなく、図形を広げる。

- 円：直径 ≧ 文字の横幅 ＋ 左右40px
- 文字が長いときは、円の**外側**にラベルを置き、引き出し線でつなぐ
- 1つの図形に入れる文字は **6文字以内**が目安。超えるなら外に出す

## 8-3-2. 主題のモノは必ず描く

そのスライドが「大画面」の話なら、**画面を描く**。「壁」の話なら壁を描く。
建物のシルエットと曲線だけの抽象図で代用しない。

抽象図で逃げていないかの判定：
**その絵を見た人が、絵だけで何の話か言い当てられるか。**
言い当てられないなら、主題のモノが描かれていない。

意味の分からない図形（棒の上の丸など）を置かない。
**描いた要素すべてについて「これは何か」を言えること。**

## 8-3-3. 循環図には向きを入れる

輪を閉じるだけでは足りない。**回る向きが分かる矢印を必ず入れる。**
円弧の途中に三角の矢じりを2〜3個置く。

---

# 8-4. 色に意味を持たせる（装飾で色を変えない）

| 色 | 意味 | 使ってよい場面 |
|---|---|---|
| `#FF6366` ピンク | 自社・解決策・強調・これから起きること | 焦点。1スライドに1つ |
| `#D6E4E7` Sub Grey | **現状・課題・従来手法・他社** | 対比の相手側 |
| `#1E1C1C` / `#5F5A57` | 中立の情報 | 本文・見出し |

やってはいけない例：

- 円環の1要素だけ色を変える（意味がないのに目立つ）
- タイムラインの最終月だけピンクにする（Month1・2が「課題」ではない）
- 順番を色分けする（順番は番号で示す）

**色を変えたくなったら、まず「これは現状か、解決策か」を自問する。**
どちらでもないなら色は変えない。

---

# 8-5. 出力の体裁

- HTMLは**改行とインデントを入れて出力する**。1行に詰めない
  （後から人が1スライドだけ直せる状態を保つため）
- スライドごとに `<!-- ══ N. タイトル ══ -->` のコメントを入れる
- CSS変数は `:root` に1か所だけ。個別スライドに生のHEXを書かない

# 9. チェックリスト

出力前に確認する。

✓ 画像の中に文字・数字・ロゴが入っていないか
✓ 彩度の高い色が、指定した1色以外に入っていないか
✓ 1スライドに文字ブロックが3つ以下か
✓ 図：テキストの比率が守られているか
✓ 実績数字がページ内最大サイズか
✓ ピンク `#FF6366` を使いすぎていないか（強調が多いと、どれも強調でなくなる。焦点は1スライド1つ）
✓ **画面の上1/3や下1/3が空いていないか**（★最も守られない。画像に書き出して確認する）
✓ **同じ図を複数スライドで使い回していないか**
✓ **図のすべての要素が、そのスライドの主張に対応しているか**（意味のない飾りがないか）
✓ **色を変えた箇所すべてに理由があるか**（現状＝Sub Grey／解決策＝ピンク。それ以外で色を変えていないか）
✓ **円環図の始点と終点が閉じているか。輪の外に飛び出した要素がないか**
✓ **循環図に回る向きの矢印が入っているか**
✓ **図形の中の文字が、図形からはみ出していないか**（円の直径 ≧ 文字幅＋80px）
✓ **主題のモノが描かれているか**（「大画面」の話なら画面を描く。抽象図で代用していないか）
✓ **図の中に、意味を説明できない要素がないか**
✓ **全スライドの密度が揃っているか**（1枚だけ詰まっていて他がスカスカ、になっていないか）
✓ **見出しの改行位置を `<br>` で指定したか**（自動折り返しで「に。」等が孤立していないか）
✓ HTMLに改行とインデントが入っているか（1行に詰めていないか）
✓ テキストがイラストに被って読みにくくなっていないか
✓ ノンブルが算用数字のみか（ラベル文字を入れていないか）
✓ 18枚通して絵柄のトーンが揃っているか

最後の項目が最も崩れやすい。
**1案件のイラストは、同じチャットの続きで生成すると絵柄が揃いやすい。**

# 10. 2026-07-29 勝ちパターン

`nakama-1910` の完成版から、HTML提案資料で再利用価値の高い勝ち筋を整理する。

## 10-1. 全面ビジュアル + 減光 + 左右どちらかに主張

- もっとも強い
- カバー、問題提起、締めに向く
- 絵は端まで断ち落とし、文字はグラデーションやスクリーンで読ませる
- 「図を見せる」のではなく「場面を体験させる」意識で使う

## 10-2. 上部または中央帯にビジュアル、下段で意味を回収

- 導入スライド、価値説明、全体像に向く
- 絵を先に見せてから下段で解釈させる
- 文章より、3つ前後のカードや短い説明で支える

## 10-3. 左右分割でも、片側は十分に大きい絵面を確保する

- 右絵・左文、または左絵・右文の2カラムは有効
- ただし「半分ずつ」では弱くなりやすい
- 実務上は 58:42 から 62:38 くらいの偏りを持たせる

## 10-4. 5機能や4ステップは、アイコン付きの均等グリッドで整理する

- 情報数が多いときの例外的な勝ち筋
- ただし、全デッキで多用しない
- 「一覧性が主役」の場面だけに限定する

## 10-5. カードだけの画面で終わらせない

- ルール適合でも、魅力は出ない
- 整ったカードは補助であり、主役ではない
- 画面の中心には、モノ、場面、変化のいずれかを置く

## 10-6. PDF導線

- 最低限: ビューアーに `PDFで保存` 操作を置く
- 推奨: 既存PDFへの `PDFダウンロード` リンクも置く
- HTMLファイル名とPDFファイル名は対応関係が一目で分かるように揃える

「印刷すれば出せます」だけでは不十分。クライアントにとっての操作導線まで設計する。
